# Brewbutler UX 体验分析与优化方案

> 版本 1.6 · 2026-11-08 · 状态：已评审（4 项决策全部完成）；原型与 UI 规范 v2.0.2 已同步；**O-01–O-12 已在代码落地并通过逐页走查**
> 输入：当前实现（`Brewbutler/UI`、`Brewbutler/App`，2026-11-07 工作树）+ [UI 规范 v2.0](ui-design.md)（Liquid Glass）+ [PRD](product-plan.md) + [技术基线](technical-notes.md)
> 本文只提方案，不改代码。凡是会改变用户可见行为的条目，都标了「需决策」，并写明要同步的文档。

---

## 0. 结论先行

当前 App 的**功能完整、安全语义扎实**：确认弹层、覆盖率口径、退出码诚实、失败可诊断都做到了。它的体验问题不在「缺功能」，而在**操作被打断、反馈渠道太多、同一个动作入口太多**。用户能做成事，但会觉得界面吵，也难判断下一步该点哪里。

v2.0 的 Liquid Glass 设计已经从结构上解决了一半问题：一级导航从 7 项收为 5 项，日志抽屉、toast、状态栏合并成任务岛，每屏只保留一个主操作。剩下一半是**行为层**的问题，换一套皮肤解决不了，需要跟 UI 重写一起改：

| # | 最该改的 5 件事 | 优先级 |
|---|---|---|
| 1 | **「检查更新」并没有去上游检查**：它只跑 `brew outdated`（只读、注入 `HOMEBREW_NO_AUTO_UPDATE`）；真正拉取上游的 `brew update-if-needed` 藏在「已安装」页工具栏菜单里 | P0 · 需决策 |
| 2 | **每个任务开始都强制弹出 308pt 日志抽屉**，批量结束时又异步弹出模态汇总 sheet，打断用户正在做的事 | P0 |
| 3 | **同一动作入口过多**：包详情里「更新」出现 4 处，Brewfile 在两个页面各有一套，仪表盘底部的快捷按钮和侧边栏重复 | P1 |
| 4 | **文案与行为不一致**：「重新安装…」带省略号，却不经确认直接入队；依赖 tab 里有一个永远禁用的「安装」按钮 | P0 |
| 5 | **筛选与开关过载**：资料库有 6 个筛选 chip、2 个 toggle 和 tap 菜单；更新页把「贪婪模式」这个偏好放在页头 | P1 |

## 1. 分析方法与范围

- **走查对象**：5 条核心用户旅程（§2），逐条对照代码中的实际行为，不以截图或 PRD 描述为准。
- **证据**：每个问题都附代码位置。代码里 `C-xx`、`D-xx`、`P0-xx` 等注释是历次评审留下的修复记录，本文把它们当作「已解决」，不重复提出。
- **评估维度**：打扰度（是否打断当前任务）、可预期性（文案与结果是否一致）、路径长度、信息密度、错误恢复、可访问性。
- **不在范围内**：视觉材质（已由 ui-design v2.0 定义）、功能增删（以 PRD 为准）、AGENTS.md §5 的硬约束（全部保留，见 §6）。

## 2. 核心用户旅程走查

### J1 · 「看看有什么要更新的」（最高频）

| 步骤 | 现状 | 体验问题 |
|---|---|---|
| 打开 App | `bootstrap()`：先探测 brew，再读缓存索引，然后 `refreshIndex()` | 好：有缓存时首屏立刻有数据（A-03 已修） |
| 点「检查更新」 | `refreshIndex()` → `brew info` + `brew outdated`，只读 scope | **结果只基于本地 tap/API 缓存**。technical-notes §2 明确说「先 `brew update` 再 `outdated` 结果最准；应区分本机已知的可更新与刚检查过的可更新」，但 UI 没有区分 |
| 想拿到最新索引 | 只能到「已安装」页 → 工具栏 ⋯ → 「更新 Homebrew 索引」（`InstalledView.swift:246`） | 入口和目的完全对不上：要更新信息，却得去「已安装」页找 |
| 自动检查 | `autoCheckUpdatesIfNeeded()`：24h 一次，同样只跑 `outdated` | 同上：自动检查也看不到上游的新版本 |

### J2 · 「把安全更新打上」

| 步骤 | 现状 | 体验问题 |
|---|---|---|
| 仪表盘看到安全卡 | 卡上有分布、覆盖率、「在更新页查看」 | 好 |
| 进入更新页 | 页头：检查更新 + 贪婪模式 toggle + 全部更新；筛选栏：4 个 chip + 「更新安全项」；每行：更新 + 预览 | 同屏 3 个「更新类」主按钮（全部更新 / 更新安全项 / 更新所选），用户要先想明白三者的范围差异（C-18 只能靠说明文字补救） |
| 执行 | 入队 → **日志抽屉自动弹出**（`TaskQueueStore.swift:557`）占据底部 308pt | 更新页本身已有逐行进度，抽屉遮住了它下方的列表 |
| 结束 | `onBatchFinished` → `batchSummary` 模态 sheet（`AppState.swift:468`） | 用户此时可能已在其他页面工作，突然被模态弹层打断 |
| 扫描状态 | 更新后已安装快照变化，漏洞缓存按快照哈希失效 | 没有提示「刚更新过，建议重新扫描以确认」，用户不知道安全卡是否还准确 |

### J3 · 「找一个新工具并安装」

| 步骤 | 现状 | 体验问题 |
|---|---|---|
| 进入发现页 | 7 项侧边栏中的第 4 项；页面有 4 个「快捷筛选」 | 快捷筛选不是真分类，需要一行免责说明（D-15）来补救，属于负价值元素 |
| 从包详情的依赖跳转 | 未安装的依赖显示禁用的「安装」按钮（`PackageDetailView.swift:480`） | 假按钮：点不了，也不告诉你去哪装。正确的下一步是「在 Homebrew 中搜索 xxx」 |
| 从任意位置搜索 | ⌘K 命令面板能搜已安装包，但远端搜索要切到发现页 | v2 的工具栏搜索 + 「在 Homebrew 中搜索」首行能解决 |

### J4 · 「这个包能删吗」

| 步骤 | 现状 | 体验问题 |
|---|---|---|
| 进入详情 | `selectPackage()` 每次都强制 `showInspector = true` | 用户关掉检查器后，换一个包又自动弹开，偏好不被记住 |
| 看操作 | 「更新到 x」出现在：页头、可更新卡、漏洞卡、检查器，共 4 处 | 重复导致视觉噪声，也让人怀疑它们是不是不同的操作 |
| 卸载 | 被依赖时禁用并解释（好）；关联文件需输入包名（好） | — |
| 重新安装 | 菜单项「重新安装…」→ `appState.reinstall()` **直接入队**（`AppState.swift:1606`，任务标记为 `isDangerous: true`） | 违反文案规则「…表示进入确认」；用户以为会有确认 |

### J5 · 「环境出问题了 / 清理空间」

| 步骤 | 现状 | 体验问题 |
|---|---|---|
| 仪表盘健康卡 | doctor 结果摘要 + 跳维护页 | 好（A-14） |
| 维护页 | 缓存、孤立依赖、doctor、missing、Brewfile、已锁定、目录 7 张卡 | 信息全，但没有优先级：「有问题要处理」和「仅供参考」混排 |
| 清理 | 先预览再确认（好） | — |
| 失败 | toast + 抽屉 + 状态栏同时反馈 | 三处讲同一件事；失败 toast 2.6 秒后消失，只能去抽屉历史里找 |

## 4. 优化方案

每条写清楚：方案 → 在 v2 UI 中的承载 → 验收（Given/When/Then）→ 改动面。

### P0 —— 跟 v2 UI 重写同批落地

#### O-01 · 让「检查更新」名副其实（U-01）· **已决策（2026-11-07）：包含 `update-if-needed`，进入变更队列**

- **方案**：「检查更新」（⌘R）拆成两段，用户只按一次：
  1. `brew update-if-needed`：作为变更类任务进入串行队列（它会写 tap/缓存）；
  2. 完成后自动跑 `brew outdated`（只读）。
  页头时间改为两个事实：「上游索引更新于 X · 本机检查于 Y」。离线或 `update-if-needed` 失败时，退回只跑 `outdated`，并显示「未能连接上游，以下结果基于 X 前的本地索引」。
- **自动检查**保持只读 `outdated`，不在用户无感知时跑 `update`（technical-notes §2：「不应在用户无感知时频繁执行」）。时间戳仍如实显示。
- **v2 承载**：更新页 hero 副标题；任务岛折叠态显示「正在同步 Homebrew 索引…」；「已安装」页去掉该菜单项。
- **验收**：Given 本地索引已过期，When 用户按 ⌘R，Then 任务岛先出现「同步 Homebrew 索引」，完成后列表刷新，页头的两个时间都更新；Given 断网，Then 出现 warning notice，列表仍可用。
- **改动面**：`AppState.refreshIndex` 增加入口参数、`updateHomebrewIndex` 串联、UpdatesView 页头文案；technical-notes §2/§4 写明「检查更新」的命令序列；PRD F12.3 验收；补「精确 argv + 失败降级」测试（AGENTS §7）。
- **已有基础**（无需新增 Core API）：`BrewClient.updateIfNeeded`（变更 scope、超时 300s）、`BrewInstallation.capabilities.updateIfNeeded` 能力探测、`AppState.updateHomebrewIndex()`（去重键 `updateIndex`）。缺口在 App 层：串联两步、记录上游同步时间、修改页头文案，以及补测试（`update-if-needed` 目前没有 argv 测试）。
- **实现要点**：① 被取消或失败时 ② 照常执行，不自动重试；brew 不支持该命令时跳过 ①；菜单栏和命令面板的「检查更新」走同一入口；自动检查不变。
- **仍需技术验证**：`update-if-needed` 在索引新鲜 / 过期 / 离线时的退出码与耗时（已列入 technical-notes §10）。
- **未采纳**：「只看本地」的轻量刷新（⌥ 点击）。可以以后再加，本次不做。
- **已同步文档**：technical-notes §2 / §2.1 / §10，PRD F4.1、F4.1b（新增）、F12.3、r5，ui-design v2.0.1（§3.4、§4.1、§4.2、§6）。

#### O-02 · 任务反馈「就近、不打断」（U-02 / U-03 / U-06 / U-15）· **已决策（2026-11-07）：采纳**

- **方案**：落实 v2 任务岛，并改掉两条行为规则：
  - **任务开始时不再自动展开**。删除 `startNext` 里的 `showDrawer = true`，改为任务岛折叠态出现，用 morph 动画吸引注意。只有用户主动点开、⌥⌘L，或从「查看日志」进入时才展开。
  - **批次汇总不再弹模态 sheet**。批次结束后任务岛进入「结果」态：`✓ 6 个包已处理 · 1 个失败 ›`；有失败就常驻，直到用户查看；点击后展开任务岛的汇总视图。系统通知只在 App 不在前台时发送（沿用现有通知设置）。
  - **失败常驻**：失败 toast 不再 2.6 秒消失，改为任务岛的失败结果态，并保持更新页行内的错误首行。
  - 状态栏与工具栏终端按钮删除，它们的信息全部由任务岛承载。
- **验收**：Given 用户在资料库页，When 后台批量更新结束且有 1 个失败，Then 不出现任何模态弹层，任务岛显示失败结果且不自动消失；点击后可看到失败包、退出码和日志。
- **系统通知（随本条确认）**：现状是 `handleTaskFinished` 对每个结束的任务都发通知，不论 App 是否在前台（`AppState.swift:1712`）；改为只在 App 不在前台时发送。
- **已同步文档**：PRD F6.2、F6.2b（新增）、r5；ui-design §4.8 / §4.10 / §5 TaskIsland 与 GlassToast 行、v2.0.1 修订记录。
- **改动面**：`TaskQueueStore`（自动展开逻辑）、`AppState.onBatchFinished`（不再写 `batchSummary` 触发 sheet，改为任务岛状态）、`ShellSheet` 去掉 `.batchSummary`（**E-17 / P1-2 的精确清理逻辑保持不动**，只是少一个来源）；PRD F6.2 验收同步。

#### O-03 · 文案与行为对齐（U-04 / U-05）

- **「重新安装…」加确认**：复用 `ConfirmSheet` 结构，标题「重新安装 openssl@3？」，说明「会重新下载并覆盖当前版本的文件，不改变版本号」，默认焦点取消。任务已标记 `isDangerous`，加确认符合 AGENTS §5.7 的精神。
- **依赖行假按钮**：未安装依赖把禁用的「安装」改为「在 Homebrew 中搜索」链接，进入发现结果页并预填包名。仍然遵守 D 注释中的约束：安装必须走发现页的确认，不从依赖行直接装。
- **全局规则写进 ui-design §6**：带「…」的按钮必须进入确认或下一步界面；不出现永久禁用且没有出路的按钮。
- **验收**：Given 任意带「…」的按钮，When 点击，Then 一定出现确认或选择界面，而不是直接执行。
- **改动面**：PackageDetailView、Sheets（新增 ReinstallSheet 或参数化现有 ConfirmSheet）、`AppState` 增加 `reinstallTarget` 并接入单一 `shellSheet`。

#### O-04 · 更新页「一个主按钮，随范围变化」（U-07 / U-12）

- **方案**：删除独立的「更新安全项」按钮，页头主按钮按当前 scope 和选择状态变化：
  | 状态 | 主按钮 |
  |---|---|
  | scope=全部，未选择 | 全部更新 36 |
  | scope=安全 | 更新 5 个安全项 |
  | scope=formula / cask | 更新 32 个 formula |
  | 有选中 | 页头主按钮让位，浮动操作栏「更新所选 3」成为唯一主操作 |
  所有路径仍先进入 BatchUpdateSheet（P0-07）。
- **贪婪模式**移到 设置 → Homebrew；开启时页头副标题显示「含自动更新的 cask」徽章，可点击跳到设置。
- **行内按钮**：保留「更新」；dry-run 预览移到行的 hover 操作和右键菜单（C-11 要求行内可达，hover 显示满足这一点；VoiceOver 用 `accessibilityAction` 暴露）。
- **改动面**：UpdatesView、SettingsView（新设置窗口）、ui-design §4.2 的线框标注主按钮规则。

### P1 —— v2 重写完成后的首个迭代

#### O-05 · 每个动作只有一个家（U-08 / U-09 / U-10 / U-18）

| 动作 | 唯一位置 | 删除的位置 |
|---|---|---|
| 更新单个包 | 详情页头主按钮 + 检查器操作区 | 可更新卡、漏洞卡里的按钮（漏洞卡改为文字链接「更新到修复版本」，滚动定位到页头） |
| Brewfile 导入 / 导出 | 维护页 Brewfile 卡 + 命令面板 | 资料库工具栏菜单（资料库只保留「导出 Brewfile」快捷按钮，v2 线框已如此） |
| 同步 Homebrew 索引 | 并入「检查更新」（O-01） | 资料库菜单 |
| 页面跳转 | 侧边栏 + ⌘1–⌘5 + 指标环 | 仪表盘底部「发现 / 服务 / 维护」快捷按钮 |
| 外观 | 设置 → 通用 | 工具栏 |

快捷键按 v2 改为 ⌘2 更新、⌘3 资料库。为老用户在首次启动 v2 时给一次性提示「快捷键已调整：⌘2 现在是更新」。

#### O-06 · 资料库筛选减负（U-11）· **已决策（2026-11-07）：采纳**

- scope 栏只保留高频且互斥的 5 项：全部 / formula / cask / 可更新 / 有已知漏洞。
- 「已锁定 / 手动安装 / keg-only / tap」收进 scope 栏右侧的「筛选 ⌄」菜单，可以组合；启用后在 scope 栏下方显示可移除的 token（「手动安装 ✕」「tap: homebrew/core ✕」），让当前筛选条件一目了然。
- 空态继续给出「清除筛选」和「在 Homebrew 中搜索」两个出路。

## 6. 不变的约束（逐条确认未被放宽）

- 不经 shell；所有新入口（O-01 的 `update-if-needed`、O-03 的搜索预填）的参数仍过 `BrewArgumentValidator`。

- 不自动重试、不自动回滚、不自动扫描：O-02 和 O-07 只提供入口。
- 漏洞文案：所有新文案仍是「本次扫描未发现 + 覆盖率 + 时间」，过时提示用 warning 语义。
- 隐私：O-10 的最近搜索只存本地，可清除，不进诊断包。
- E-17 / P1-2 的单一 sheet 精确清理逻辑保留；O-02 只是减少一个来源。
